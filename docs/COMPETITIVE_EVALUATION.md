# Competitive evaluation (Phase AA)

What TraceJIT can be compared to, what could not be compared, and what the
comparison actually shows. Machine-readable evidence:
`benchmarks/results/phaseaa/competitive.json`; generated by
`benchmarks/realworld_v2/competitive.py`.

## 1. Tools examined

| Tool | Role | Available | Pinned version for comparison | Why it matters |
| --- | --- | --- | --- | --- |
| ccache | compiler cache | **no** | 4.9.1 | The direct competitor for the one niche where TraceJIT wins |
| sccache | compiler cache | **no** | 0.8.2 | Same, with remote storage |
| ninja | build scheduler | **no** | 1.11.1 | Scheduler comparison, like `make` |
| firebuild | process-level build accelerator | **no** | 0.9.0 | Closest in mechanism to TraceJIT |
| zstd | compression | **no** | 1.5.5 | Corpus workload, not a competitor |
| perf | hardware counters | **no** | kernel-tools | Independent counter cross-check |
| hyperfine | independent wall clock | **yes** | 1.19.0 | Used for the cross-check in §5 |
| make | build scheduler | **yes** | GNU Make 4.3 | Scheduler baseline on the same command |

The image has no root and no prebuilt static archives for ccache, sccache, ninja
or firebuild. **No relative-speed claim is made about any of them.** An
uninstalled tool cannot be shown to be slower, and a tool run with a materially
different configuration is not a fair comparison. This is the single largest gap
in the competitive evidence and it is reported as such rather than filled with an
estimate.

Consequences for interpretation: the Phase AA result "TraceJIT reuses 17/49
compiler workloads at 6.9–7.4× over direct execution" says nothing about whether
ccache would do better on the same commands at a fraction of the hit cost. On
mechanism alone, a compiler cache keyed on inputs plus preprocessed source
normally costs single-digit milliseconds and stores exactly the compiler's
output; that is the burden of proof TraceJIT has to meet, and Phase AA cannot
settle it. Phase AB should treat "measure ccache on `gcc-cc-heavy-tu`" as a
release blocker for any competitive claim.

## 2. Mechanism taxonomy

These are not interchangeable, and the tables below say which one acted:

- **Build scheduler** (`make`, `ninja`): compares timestamps and decides to skip.
  Does not look at outputs, cannot detect a corrupted or truncated result, and
  cannot help when the output was deleted.
- **Compiler cache** (`ccache`, `sccache`): intercepts the compiler, hashes the
  preprocessed source and flags, restores the object file. Needs compiler
  cooperation and only covers compiler invocations.
- **Traced whole-command cache** (TraceJIT, Firebuild-class): observes a process
  tree, records inputs/outputs, validates them and replays. Covers arbitrary
  commands in principle, at the cost of a validation pass over everything the
  command read.
- **Domain-specific caches**: not evaluated.

A fast result from *skipping* work is not equivalent to verified cached replay.
Both appear below with the mechanism named in the row.

## 3. Same command, three situations

`gcc -O2 -I zlib-1.3.1 -c zlib-1.3.1/adler32.c -o adler32.o`, with a real
Makefile rule for the same command. Correct output SHA-256
`dbc636068b611e09…`. TraceJIT ran under `compiler-runtime-v1`; its decisions were
`Reused` in every row below, verified from its JSON report — not inferred.

| Situation | make | TraceJIT | What it means |
| --- | --- | --- | --- |
| output absent, 12 rebuilds | executed gcc each time, 1162.8 ms total (96.9 ms/run) | **897.2 ms total (74.8 ms/run)**, 12/12 `Reused` | restoring beats recompiling by **1.29×** |
| output present, 12 reruns | skipped, **28.1 ms total (2.3 ms/run)** | 963.4 ms total (80.3 ms/run), 12/12 `Reused` | make's decision is **35× cheaper** — it does not validate anything |
| output corrupted | skipped again, **left the corruption in place** | `Reused`, restored the correct bytes | only one of the two protects the output |

This is the honest shape of the competition. TraceJIT is not a faster `make`: on
the cheap decision it is far more expensive, because it re-validates every
recorded dependency. It wins only when re-execution is expensive *and* the output
is missing or damaged — and it wins there because `make` cannot notice damage at
all.

Related observation from the corpus (`output_corruption` rows): corrupting an
output makes TraceJIT **retrace** for commands that open and read their own
output (`gzip -f`, `bzip2 -f`, `objcopy`, `strip`) and **restore** for commands
that only create it (`gcc`). Both are correct. Reporting only the `gcc` case would
overstate how often a corrupted output is repaired by restoration.

## 4. Ineligible command: what tracing costs when it is refused

`make-build` (a full multi-target build) is refused by TraceJIT under all three
policies on this host.

| Arm | Per invocation | 12 invocations |
| --- | ---: | ---: |
| native `make` | 85.3 ms | 1089.5 ms |
| through `tracejit run` | 545.4 ms | 6440.4 ms |

**+460 ms per invocation, 6.4× the build.** Tracing a command that is then
refused is not free: the observation itself is the cost. Practical rule, which
belongs in the documentation: do not wrap ineligible commands. A user who puts
`tracejit run` in front of `make` unconditionally makes their build several times
slower.

## 5. Independent wall-clock cross-check

hyperfine 1.19.0, same pinned input, `gzip -6 -n -c corpus.txt`:

| Command | Median | Mean |
| --- | ---: | ---: |
| native gzip | **6.17 ms** | 5.80 ms |
| `tracejit run … gzip` | 24.35 ms | 23.81 ms |

Both arms run through a shell, so the absolute numbers include shell overhead;
the comparison is still valid because both pay it. This independently reproduces
the corpus result that a cheap compression command is ~4× slower through
TraceJIT, and it confirms the harness is not measuring something the shell does
not see. hyperfine's numbers are noisier than the paired harness because it cannot
pair samples, which is why the corpus uses paired ratios as its primary evidence.

## 6. Hashed environment and cache relocation

`TRACEJIT_CACHE_DIR` is part of the inherited environment, and the environment is
hashed into the execution identity. Copying a cache to a different directory
therefore makes every record ineligible: a relocated cache produced `Executed`,
not a hit, in two reproductions. This is a real usability and evaluation hazard —
it silently voids results whenever the cache is moved, and it is why every
benchmark here pins `TRACEJIT_CACHE_DIR` per workload and records it in the
schema. Not fixed in Phase AA; listed in the release-readiness blockers.

## 7. What the comparison supports

- TraceJIT is **not** a transparent replacement for `make`, `ninja`, `ccache` or
  `sccache`. It is a different mechanism with a different cost profile, and on the
  cheap-decision axis it is much more expensive.
- It **does** something none of the available baselines do: it detects a corrupted
  or missing output and repairs it with verified bytes, for arbitrary commands,
  without compiler cooperation.
- Whether that is worth 80 ms per hit depends entirely on the command's direct
  cost. On this corpus it pays for compute-heavy work and large translation
  units, and loses for everything cheap.
- No claim is made about ccache, sccache, ninja or firebuild. That comparison
  requires installing them, which this environment cannot do.
